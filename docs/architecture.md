# EstateAtlas architecture

## Decisions

TypeScript / pnpm monorepo: Next.js App Router web, Expo React Native for native Android/iOS, Fastify REST API, real PostgreSQL. Shared Zod 4 validation, property models and currency-aware statistics; shared fetch client used in both apps. Native stack + bottom tabs and react-native-maps; Leaflet + marker clustering in web. No service worker, PWA manifest or mobile web substitute.

A single PostgreSQL database holds users, hashed sessions, properties with owner/member roles, valuation history, private binary attachments, analysis jobs and quota reservations, versioned workspaces, and hashed invitation codes. SQL uses parameters and explicit owner/member predicates. Property mutation and history writes run transactionally. Docker Compose is the default runtime. PostgreSQL 18 uses a named volume, SCRAM and a separate non-superuser app role; secrets are file mounts. The original `.local/` host cluster is retained as the migration source and rollback option. Production can supply DATABASE_URL to a managed/self-hosted PostgreSQL without changing the apps.

## Identity and confidentiality

Scrypt password hashes (N=32768, r=8, p=3; [OWASP memory/CPU-balanced configuration](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt)) with random salts and bounded inputs. Random 256-bit session tokens are hashed in the database, expire after seven days, and are revoked on logout. Web uses HttpOnly SameSite=Lax cookies; native uses bearer sessions persisted in Expo SecureStore. Production cookies require HTTPS. Cookie mutations require an exact allowlisted Origin; registration/login require it for the browser too. CORS grants only the configured WEB_ORIGIN. Rate limiting, request limits, security headers and error redaction apply. No public portfolio or attachment URLs. File content is checked (JPEG/PNG/WebP/PDF), limited, stored privately and served with nosniff. Password reset, verified email changes, MFA with recovery codes, session management, beta invitations, platform administration and owned-data export/deletion are implemented; see [accounts-admin.md](accounts-admin.md). Malware scanning and external production infrastructure remain release work. Scrypt concurrency is bounded to protect the small API container.

## Property and portfolio rules

GPS comes from an explicitly selected address suggestion, map click/pin adjustment, or manual entry. Editing the address text invalidates old coordinates. Addresses, type, price, currency, area, year, amenities, condition, notes and archival state share one validated model. Prices are user-entered estimates, labeled accordingly. Dashboard totals and changes are grouped by currency, without invented exchange rates. Histories are dated snapshots of user input, never generated past appreciation. Archive preserves data; deletion cascades histories, attachments and jobs. Test fixtures are explicitly labeled and opt-in per authenticated account.

## Rental status and recorded value history

Properties optionally store `rental` in their existing JSONB data: `null` means unspecified, `vacant` has no dates, and `rented` requires a calendar start date with a nullable end (unlimited). Shared Zod validation rejects invalid or reversed dates. Existing records are returned with `rental: null`; no fabricated occupancy or database migration is needed. Shared labels distinguish future, ongoing (including its end day) and ended periods. Dates are calendar dates without a time zone; status boundaries use the UTC calendar day. Web and native editors, cards and details share the model. Rental fields do not collect tenant identities or rent payments; users may optionally upload their own documents in the separate private attachment area. Rental fields are excluded from the existing minimal OpenAI snapshot and do not create valuation rows.

Both property-detail views plot recorded `valuations` with shared time/value geometry, a selectable currency and all/365-day/30-day windows. Change and percentage compare the first and last actual observations in the selected window; missing/zero baselines produce no invented percentage. Currencies are never summed or converted. A single record shows a point and no trend; gaps contain no generated observations. The joining line is a visual guide, not an observed daily market series. Web supports point selection with a keyboard-accessible slider and the recorded-values list; native supports point taps and a pressable values list. Existing value edits and explicit research adoption feed the history automatically; no API call, AI request, fabricated past value or new valuation endpoint is introduced.

## Address search

Web and native editors debounce typed queries (minimum four characters); existing addresses are never automatically sent. A protected POST `/geocoding/search` sends only the search text through the API to [Photon](https://github.com/komoot/photon), which explicitly supports search-as-you-type with OpenStreetMap data. The UI identifies the service and credits OpenStreetMap. Queries stay out of request URLs/API request logs and the database. Server-side `GEOCODING_URL` selects a fixed trusted endpoint, never a client-supplied URL. This permits switching to a dedicated instance without client updates. The public demo permits moderate use without an availability guarantee; the public Nominatim service is not used for autocomplete.

Requests require the same authentication and browser CSRF checks as other private API operations. A per-route rate limit plus a global one-request-per-second/in-flight guard limits provider use; a bounded 200-entry, ten-minute per-account RAM cache avoids duplicate requests. Provider errors/timeouts produce a localized fallback rather than made-up coordinates. GeoJSON longitude/latitude order, range, ISO country, field lengths and result count are validated. Approximate street/place matches are identified. Selecting a suggestion updates address, country and coordinates together; dragging/tapping the pin updates only coordinates. Web uses Leaflet; native uses react-native-maps. Pin placement remains available when search fails.

## Maps

Web and native default to local, generalized Natural Earth 1:110m country polygons with shared Mercator geometry, muted colors and portfolio pins/clusters. Web renders GeoJSON in Leaflet; native renders SVG with pan/zoom and pressable portfolio markers. No external tile requests occur in this mode. Public-domain data provenance is recorded beside the bundled dataset. Simplified zoom is capped at approximately level 6 because this is an overview, not street/cadastral geometry.

The detail toggle preserves private records, filters and coordinates. Web detail mode loads OpenStreetMap raster tiles with a local light theme, accessible zoom controls and fit-filtered-portfolio button. Attribution and standard browser caching remain intact; no prefetch/offline downloads, following [tile policy](https://operations.osmfoundation.org/policies/tiles/). Tile providers see IP and viewed map area. Editor details focus the selected pin for precise adjustment.

An optional public, website-restricted `NEXT_PUBLIC_CARTO_MAPS_KEY` selects CARTO Positron raster tiles using the current [documented URLs](https://www.carto.com/basemaps/). Public Next.js variables are bundled at build time; rebuilding is required after changing the key. No provider account or paid plan was created. A CARTO tile error switches once to OSM, updates attribution, removes the CARTO layer and announces the fallback. Provider choice does not affect private property data or pin selection.

Native detail maps use Apple Maps on iOS with `mutedStandard`, and Google Maps on Android with a local light JSON style, shared by portfolio and editor. These do not use CARTO or pretend to be pixel-identical. Development in Expo Go does not require creating a paid service. A standalone Android binary needs a reviewed Google Maps key and restrictions before distribution. GPS/filtering data is identical; implementations differ. Both native styles still need real-device visual and gesture checks.

## Analysis extension

Analysis jobs are persisted with a minimal property snapshot, owner-controlled execution and collaborator-readable results, model/provider, real phases, reason, result and usage. A Docker worker claims jobs with PostgreSQL SKIP LOCKED, heartbeats and a three-minute timeout. Interrupted paid requests fail rather than automatically retrying. Only explicitly consented user requests enter the queue; global/personal rolling daily reservations survive property deletion. OpenAI Responses performs web research and separate strict extraction with bounded tool calls/output and store:false. The ResearchProvider interface separates providers from queue/business logic. Shared rules calculate comparison medians/ranges; neither API nor model overwrites a property value automatically. Adoption is owner-checked, transactional and idempotent, and rejects changed attributes/currency. Clients share configuration, phase/result contracts and HTTP methods. See docs/ai-research.md for exact activation, limits and evidence caveats. The first owner-initiated live request reached calculation but produced insufficient accepted comparisons. Migration 003 persists bounded private research artifacts, usage and owner-visible rejection diagnostics before calculation, including failures. Quality remains unverified; no automatic paid retry or daily-reservation reset is allowed.

## Environment and verification

Dependencies are pinned in pnpm-lock.yaml. Node 22 is installed only within this project and verified against the upstream checksum. Builds and test artifacts stay ignored. API tests use an isolated real PostgreSQL database/cluster; browser tests cover real authentication and persisted property changes. Browser test servers use ports 3001/4001 and a separate `.next-e2e` Webpack build, so the live development apps on 3000/4000 stay independent. Third-party geocoder responses in tests are labeled fixtures; they never send synthetic/private addresses to Photon. Compose builds production API and Next standalone artifacts sequentially on the small VPS. Tests can run locally in isolated clusters. Next standalone is also exercised by the browser-test server. An explicit loopback-only HTTP-cookie exception permits SSH testing of container artifacts; public deployment retains HTTPS security. See docs/docker.md for migration and operation. Both native platforms get Metro exports; exports prove JS bundling, not a device install or an App Store/Play build.

Official references consulted: [Next installation](https://nextjs.org/docs/app/getting-started/installation), [Expo SDK compatibility](https://docs.expo.dev/versions/latest/), [Expo monorepos](https://docs.expo.dev/guides/monorepos/), [Fastify validation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/).

## Collaboration and property workspaces

Migration 004 adds `property_workspaces`, `property_members`, and `property_invitations`. Existing properties remain owned by their original account. `Property.access` is derived server-side; input schemas never accept ownership or role claims. Read APIs list owned or explicitly shared records; both clients default their financial metrics to owned records. Viewer membership permits private property/history/workspace/asset/result reads. Editors can change property data, workspace content and attachments. Archive/delete, membership administration and all paid research actions remain owner-only.

Invitation codes are random 256-bit single-use capabilities delivered manually by the owner, stored only as hashes, and consumed by a signed-in user within seven days. No outbound email integration is required. Membership changes and editor mutations use the same property row lock before rechecking authorization. Workspace saves compare an expected version under that lock and return 409 on conflicts. Content has shared validation and bounded size; the HTTP route allows sufficient UTF-8 bytes for valid content. Revoking a member blocks subsequent API operations; already downloaded files cannot be recalled.

Checklists store real dates, task completion and optional notes. Purchase planning is a separate persisted scenario with its own currency and explicit cost assumptions, rounded per currency. Changing a property's currency does not convert a saved plan. These features never start research or add inferred past valuations. See `docs/portfolio-workspace.md` for the role matrix and current limits.
